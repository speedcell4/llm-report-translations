1. 引言

近年来，大语言模型（LLM）（Anthropic, 2024; Dubey et al., 2024; Hurst et al., 2024; Team et al., 2024a）和视觉语言模型（VLM）（Anthropic, 2024; Dubey et al., 2024; Hurst et al., 2024; Team et al., 2024a）迅速发展，在知识问答、复杂推理、数学、编程以及视觉语言理解等任务中表现出色。当前大多数模型的上下文窗口介于 32K 至 256K token 之间。然而，这些长度往往无法满足实际需求，例如将一本专业书籍用作上下文、辅助完成整个编程项目，或者通过大量示例最大限度发挥上下文学习的潜力。

过去两年，上下文窗口的扩展主要得益于更强大的 GPU 和更好的 I/O 感知 softmax attention 实现（Dao et al., 2022; Liu et al., 2024a）。然而，进一步扩展这些窗口已被证明十分困难。这一限制源于 transformer（Vaswani et al., 2017）架构固有的二次计算复杂度：继续增加长度会使计算需求的增长速度远超硬件能力。为应对这一挑战，研究者提出了多种降低 attention 机制计算复杂度的方法：稀疏 attention（Beltagy et al., 2020; Zaheer et al., 2020）、线性 attention（Qin et al., 2022a,b, 2024c）、长卷积（Qin et al., 2023a）、状态空间模型（Mamba 系列）（Dao and Gu, 2024; Glorioso et al., 2024; Gu and Dao, 2024; Ren et al., 2024; Team et al., 2024b），以及线性 RNN（Qin et al., 2023b, 2024d）。尽管理论前景良好，这些创新在商业规模模型中的采用仍然有限。

在本报告中，我们旨在构建一个性能与领先商业模型相当、上下文窗口却长一个数量级的模型。这一雄心勃勃的目标要求仔细平衡网络架构、数据和计算等多种因素。

我们首先选择最有潜力的架构，然后优化底层训练与推理框架以确保对其提供支持。对于网络架构，我们要求线性 attention 不仅在理论上合理，而且在实践中高度高效，尤其是面对长上下文时。经过大量实验，我们确定了一种主要采用 lightning attention（Qin et al., 2024b）的混合架构；lightning attention 是一种线性 attention 变体（Qin et al., 2022a）的 I/O 感知实现。在这一架构中，每七个采用 lightning attention 的 transnormer block（Qin et al., 2022a）之后，接一个采用 softmax attention 的 transformer block。

我们依据一项实际约束确定模型总参数量：使用 8 位量化时，能够在最多配备 8 块 GPU、总显存为 640GB 的单台机器上处理超过 100 万 token。为了最大化参数容量与计算容量，我们采用了混合专家（MoE）（Fedus et al., 2022; Lepikhin et al., 2021）。我们综合考虑训练资源、推理资源与最终模型性能，力求在三者之间取得更好的平衡。大量实验引导我们确定了最终模型规格：4560 亿参数、459 亿激活参数和 32 个专家。

现有分布式训练与推理框架主要针对 softmax attention 优化。然而，我们融合 lightning attention、softmax attention 和 MoE 的新架构，要求彻底重新设计训练和推理框架。此外，框架必须能够支持数千亿参数模型和百万 token 级上下文窗口的训练与推理。为此，我们利用专家并行（EP）与专家张量并行（ETP）实现 MoE 中的 all-to-all 通信，旨在尽可能降低 GPU 之间通信的开销。为了支持无限扩展的上下文窗口，我们设计了变长 ring attention 以减少冗余计算，并改进了线性 attention 序列并行（LASP）（Sun et al., 2024），以充分发挥设备的并行能力。此外，我们还实现了

2. 模型架构

本节介绍我们的网络架构设计。为了在资源受限的条件下取得最佳性能，并更好地处理较长序列，我们采用 MoE 方法，并尽可能使用线性 attention，替代标准 transformer 中传统的 softmax attention。

为了便于直观理解，图 3 展示了主要架构。我们的设计遵循 Transformer 风格的 block，每个 block 包含通道混合器（attention block）和特征混合器（MLP block）。我们采用两种通道混合器：lightning attention 和 softmax attention。特征混合器是包含多个前馈网络（FFN）的 MoE。为了确保 MoE block 中的负载均衡，我们提出了一种受 GShard（Lepikhin et al., 2021）启发的新负载均衡策略，称为全局路由器。该策略旨在维持训练稳定性。此外，我们集成 DeepNorm（Wang et al., 2024a）以提升整体性能。

最终 MiniMax-Text-01 架构按照结构化模式融合线性 attention 与 softmax attention。具体而言，每 7 个采用线性 attention 的 transnormer block（Qin et al., 2022a）之后放置一个采用 softmax attention 的 transformer block，共计 80 层。每个 attention 模块包含 64 个 head，每个 head 的维度为 128。softmax attention 层使用分组查询 attention（GQA）（Ainslie et al., 2023），组大小为 8。旋转位置 embedding（RoPE）（Su et al., 2024）应用于 attention head 维度的一半，基频设为 10,000。模型隐藏维度设为 6144，每层包含 32 个专家，采用 top-2 路由策略。每个专家内部前馈网络的隐藏维度为 9216。MiniMax-Text-01 总计包含 4560 亿参数，每处理一个 token 激活其中的 459 亿参数。

接下来的章节将详细介绍模型架构方面的考虑，即不同 attention 机制的融合、MoE 与线性 attention 的协同作用、超参数选择的依据，以及基于 scaling laws 确定模型规模的方法。

2.2. 线性 Attention

线性 attention 利用“右乘核技巧”将二次计算复杂度转换为线性复杂度，如图 5 所示。以 TransNormer（Qin et al., 2022a）为例，其 NormAttention 机制可以写为：

\[\mathbf{O}=\operatorname{Norm}((\mathbf{Q}\mathbf{K}^{\top})\mathbf{V}).\tag{2}\]

其中 \(\mathbf{Q},\mathbf{K},\mathbf{V}\in\mathbb{R}^{n\times d}\) 分别为 query、key 和 value 矩阵，\(n\) 为序列长度，\(d\) 为特征维度。该等式可以通过矩阵右乘转换为线性形式：

\[\mathbf{O}=\operatorname{Norm}(\mathbf{Q}(\mathbf{K}^{\top}\mathbf{V})).\tag{3}\]

这一线性表达式能够实现高效的递归预测，训练复杂度为 \(O(nd^2)\)。此外，线性 attention 确保计算复杂度保持为常数 \(O(d^2)\)，与序列长度无关。这通过递归更新 \(\mathbf{K}^{\top}\mathbf{V}\) 项实现，因而无需重复计算整个 attention 矩阵。相比之下，softmax attention 在推理期间的复杂度为 \(O(nd^2)\)。

在处理因果语言建模任务时，右乘的有效性受到限制，需要计算 cumsum（Hua et al., 2022）。这一限制妨碍了高效并行计算的实现，这或许解释了为何尽管 Brébisson 等人（de Brébisson and Vincent, 2016）早在九年前就提出该方法，当前领先的开源 LLM，包括 LLaMA3（Dubey et al., 2024）、Qwen2.5（Yang et al., 2024）、DeepSeekV3（DeepSeek-AI, 2024）和 Mistral（Jiang et al., 2023），仍未采用这一线性 attention 机制。

2.2.2. Lightning Attention 的有效性

尽管 lightning attention 在小规模实验中表现出潜力和有竞争力的性能，但其在大规模条件下的扩展行为和下游任务能力尚未探索。为了填补这一空白，我们进行一系列扩展实验，评估 lightning attention 机制相对于 softmax attention 的可扩展性，同时验证其在广泛下游任务上的性能。值得注意的是，实验中我们观察到 lightning attention 的检索能力有限。这一发现促使我们探索一种混合方法（Hybrid-lightning），结合 lightning attention 与 softmax attention 的优势：每隔八层用 softmax attention 替代 lightning attention，以增强检索性能。

3. 计算优化

本节介绍计算部分，包括训练与推理。本项目的 GPU 集群动态变化，H800 GPU 数量介于 1500 至 2500 之间。高效架构需要强有力的实现优化，以充分发挥大规模下的计算优势。为了将新架构扩展至所需规模，我们提出三项关键优化策略，主要应对以下三项挑战：

  1. 降低混合专家（MoE）架构训练中的 all-to-all（a2a）通信开销始终是一项挑战。我们选择的专家配置，尤其是选择大型模型，对 GPU 显存提出了很高需求。因此，主要挑战是在显存使用、计算效率与 all-to-all 通信开销之间取得最优平衡。
  2. 我们力求在训练与推理中支持至少 100 万 token 的上下文窗口，因此对于这一庞大模型，必须将如此长的上下文中的 token 准确分布到不同 GPU 上。然而，这不可避免地引入额外通信开销。因此，设计降低这种开销的策略，尤其是在我们的混合架构下，是一项重大挑战。
  3. 当前 lightning attention 机制的实现专门针对训练过程优化。然而在推理场景中，挑战在于有效管理真实的 batch 输入，其中可能包含不同序列长度，以及使用前缀缓存的特定输入。

值得注意的是，业内现有开源框架尚缺乏足够成熟的技术支持，无法充分应对这些挑战。因此，我们独立、全面地重新构建分布式训练与推理框架，从而以所需效率成功解决这些挑战。

长上下文训练的一项重大挑战是，真实训练样本难以统一为相同长度。传统方法通过 padding 将样本补齐到同一长度，会造成大量计算浪费。在 1M 序列长度规模的训练中，这种浪费尤其显著。为解决这一问题，我们在训练期间采用数据格式化技术，沿序列维度将不同样本首尾拼接，称为“数据打包”。这种格式减少计算过程中的浪费，从而节约计算资源。

lightning attention 机制的最初实现主要面向研究，尚不适合实际应用，尤其是推理。然而，推理过程优化对真实场景至关重要，因为已训练模型的长期部署成本主要由推理效率决定。为此，我们针对 lightning attention 实现四项优化策略：batch kernel 融合、prefill 与 decoding 分开执行、多级 padding，以及 strided batched matmul 扩展。

3.3.1. Batch Kernel 融合

我们融合多个受显存带宽限制的 kernel，并扩展支持以容纳所有 batch 输入。在 prefill 阶段，我们融合处理 \(Q,K,V\) tensor 的 kernel，包括序列维度 padding、划分块、调整内部布局和计算衰减值。在 decoding 阶段，我们融合计算 \(KV\) 与更新前缀 \(KV\) cache 的 kernel。这些融合减少中间结果存储与显存访问，显著提高显存访问效率，并在 decoding 阶段及短文本输入场景下降低 10% 的端到端延迟。另外，相比 H800，这些优化在 H20 上可以带来非常明显的收益。

3.3.2. Prefill 与 Decoding 分开执行

lightning attention 机制的长序列计算实现主要围绕区分块内与块间计算展开。然而，对于推理任务，这一方法并非最优，尤其在 token 长度恒为 1 的 decoding 阶段。

长度为 1 的 token 的计算 kernel 主要受显存带宽限制，且只需要有限数量的 GPU 流式多处理器（SM）。因此我们提出一种策略，将长度为 1 的 token 与长度大于 1 的 token 分开处理，通过两个不同 kernel 实现。随后，利用两个独立 CUDA stream 并行调度这些 kernel，提高计算效率并确保 GPU 利用均衡，尤其是在混合输入场景中。

例如，batch 大小为 20，所有输入都包含前缀 key-value（KV）cache，其中一两个输入的 token 长度为 50，其余为 1，这种方法可显著降低延迟。具体而言，延迟可以约等于只处理较长输入的延迟，表现为从 100 毫秒降低到 50 毫秒。

3.3.3. 多级 Padding

沿序列维度对 \(Q,K,V\) tensor 进行 padding，可以将块内与块间部分有效分解为多个相同的矩阵乘法。这尤其有利，因为它与 StrideBatchedMatmul 接口无缝匹配，从而最大限度发挥并行处理能力。

最初，padding 的块大小设为 256，与训练参数一致。然而，实现前缀 cache 技术后，观察到 batch 内 token 长度通常小于 256，导致每个矩阵乘法操作中出现冗余计算。为解决低效问题并尽可能减少不必要计算，我们提出增加分段选项，具体为 32、64 和 128。

这种多级 padding 方法根据当前输入序列长度，动态选择 padding 开销最小的计算规模。采用这一方法可优化计算资源利用，确保系统以更高效率、更少冗余运行。这一策略调整不仅节约计算资源，还提升系统整体性能。

3.3.4. StridedBatchedMatmul 扩展

我们使用 NVIDIA cuBLAS 库中优化后的 cublasGemmStridedBatchedEx 函数管理 StridedBatchedMatmul 操作，确保在不同硬件架构上具有高性能与通用性。同时，我们正实施更加广泛的 kernel 融合策略，旨在显著提升 Hopper GPU 的计算效率。

由于序列划分块大小配置为 256，涉及 256×256 矩阵的相关通用矩阵乘法（GEMM）操作可以利用 warpgroup 范围的 WGMMA 指令进行计算。为进一步提高显存访问效率，我们集成 Tensor Memory Accelerator（TMA）的异步操作，并将部分预处理与后处理计算任务交由 CUDA Core 异步执行。

最终目标是动态调节流水线阶段数量，自适应地在 H20 和 H800 GPU 架构上取得最佳性能。这种自适应控制机制将确保系统高效处理不同工作负载与硬件配置，最大限度提高整体计算吞吐量和资源利用率。

通过上述优化，我们在 H20 GPU 的端到端推理任务上实现超过 75% 的模型 FLOPs 利用率（MFU）（Chowdhery et al., 2023）。具体而言，在 MiniMax-Text-01 与 MiniMax-VL-01 推理中，考察 MoE 结构内 attention 操作与前馈网络（FFN）操作的延迟比例，当序列长度为 1,024,000 token 时，softmax attention 占延迟的 95%。相比之下，同样条件下 lightning attention 实现所占延迟低于 12%。

我们的 lightning attention 实现在管理具有不同序列长度的异质 batch 输入时展现了显著效率，尤其是在部分输入采用前缀缓存策略、其余不采用的场景中。延迟降低不仅加快了整体推理过程，还确保系统以极小性能损失处理广泛输入类型。这种适应性凸显了 lightning attention 方法在实际应用中的稳健性与通用性。

我们引入离线 RL 阶段，即直接偏好优化（DPO）（Rafailov et al., 2023），以优化模型在多样 prompt 分布上的表现，因为它简单，而且长上下文场景中的数据易于构建。特别关注与 SFT 阶段使用的 prompt 保持分布一致的 prompt。为评估 prompt 选择的影响，我们比较两类 prompt：已用于 SFT 训练的 prompt，以及未用于 SFT 训练但同源的 prompt。实证表明两者性能差异可以忽略，因此离线 RL 阶段采用已用于 SFT 训练的 prompt。实验对每个 prompt 使用不同温度参数生成回答，然后通过第 5.2 节所述奖励模型系统评估。接着选出最佳与最差回答，构造 DPO 训练的偏好对。

5.4.2. 在线强化学习

相比离线学习，在线学习具有更高样本效率与跨领域泛化能力。因此我们采用在线 RL，提升模型性能，尤其是数学推理能力。方法强调 prompt 多样性，并优先选择成功率适中的 prompt，以最大化策略更新中的信息增益。值得注意的是，在线 RL 中使用未经过 SFT 训练的 prompt，因为实证观察表明，重复使用前阶段的 prompt 会使模型饱和，表现为回答困惑度下降。我们提出改进的组相对策略优化（GRPO）（Shao et al., 2024），包含以下关键创新：

  • 重要性采样权重裁剪。传统 PPO/GRPO 实现采用单侧裁剪（Schulman et al., 2017; Shao et al., 2024），处理策略比率大且 advantage 为负的 token 时，有时会导致 gradient 不稳定。为此，我们实施额外裁剪，在损失函数中舍弃这种情况，有效控制重要性采样幅度并减轻噪声传播。
  • KL 散度优化。针对相似的 gradient 不稳定问题，我们通过对方差与偏差权衡的理论分析重新表述 KL 散度项，进一步稳定 gradient 行为，得到 \(\mathbb D_{KL}(\theta)=\mathbb E_t[\operatorname{SG}(\pi_\theta(a_t\mid s_t)-\pi_{ref}(a_t\mid s_t))\log\pi_\theta(a_t\mid s_t)]\)，其中 \(\operatorname{SG}(\cdot)\) 表示停止 gradient 算子。这一表达式在降低 gradient 方差的同时保持策略一致性。
  • 均衡 Advantage 估计。我们还确保正例与负例之间的奖励贡献公平，这在分布偏斜的场景中尤其有效。通过调节不同样本组奖励的绝对幅度，保持训练动态稳定。

6.2. 架构

6.2.1. 整体架构

MiniMax-VL-01 架构遵循许多多模态大语言模型（MLLM）广泛采用的“ViT-MLP-LLM”范式，包含三个主要部分：用于视觉编码的 3.03 亿参数 Vision Transformer（ViT）、用于图像适配的随机初始化两层 MLP 投影器，以及作为基础大语言模型的 MiniMax-Text-01。

我们实施动态分辨率策略，按预定义网格配置列表调整输入图像大小，范围为 336×336 至 2016×2016，同时保留分辨率为 336×336 的标准缩略图。调整后的图像划分为不重叠的 336×336 patch。图像 patch 与缩略图分别编码，将编码特征拼接成全面的图像特征表示。

不同于依赖池化或其他下采样技术压缩特征表示的传统方法，我们利用模型强大的长序列处理能力，在训练中直接使用原始高维特征。这缓解潜在信息丢失，大幅提升对多尺度输入的适应性。此外，通过将 patch 与缩略图投影到统一特征空间，我们的方法显著增强处理多样复杂视觉输入时的稳健性与表示能力。

我们以轻量级 ViT-L/14（Dosovitskiy et al., 2021）作为视觉编码器基础结构，从头训练。遵循标准流水线，输入图像 tensor 首先通过卷积层提取独立 patch，随后加入绝对

6.3. 训练方案

我们采用四阶段训练策略，使模型在保持语言理解能力的同时逐步获得全面的多模态理解能力。此外，问答、指令遵循以及人类偏好对齐能力，在各阶段系统地完善。

阶段 I：模态对齐。主要目标是让模型准确生成给定图像的合适 caption，实现视觉 token 与文本 token 对齐。为此，更新图像适配器与视觉编码器的权重，优化其多模态表现。本阶段使用从图像描述数据集中采样的总计 800 亿 token。实证发现，提高图像分辨率不能改善下游准确率，因此统一以 336×336 分辨率处理图像，降低计算成本。

阶段 II：增强视觉理解。可视为标准指令微调阶段，所有模型参数均可更新。主要目标是让输出符合人类指令，增强执行多样视觉理解任务的能力。使用从指令数据集中采样的 4200 亿多模态 token，并以 20:1 比例结合 MiniMax-Text-01 后训练数据，确保获得新多模态能力的同时保持语言建模能力。

阶段 III：增强用户体验。本阶段进一步增强真实场景及困难用户输入下的能力。我们从人们常用应用中获取图像，构建复杂多模态数据。精细标注对话，模拟真实用户输入，确保多轮对话中提供准确、有用、多样的回答。数据构建由独立人工标注测试集指导，不仅优先考虑准确率，还考虑用户体验方面的整体质量。所得数据集包含 448 亿多模态 token，训练一个 epoch。

阶段 IV：增强偏好。最后采用直接偏好优化（DPO），进一步提升性能与用户体验。通过以下过程构建包含 40,000 个图文对的训练集：

  • Prompt 选择。从指令数据和真实用户交互数据中精选 prompt，覆盖广泛通用场景，并专门解决

  • 回答生成。采用多样策略，包括改变采样温度生成多个候选回答；在特定场景通过弱化图像创建回答变体；以及在特定场景使用 MiniMax-Text-01 故意向高质量回答引入幻觉或错误，生成对照样本。

  1. 长上下文评测：当前长上下文检索数据集主要针对人工或简化场景设计，而在文档分析等实际应用中，长文本推理能力评估仍然有限。计划在更真实场景增强长上下文检索，并将推理评测扩展到更广任务。
  2. 模型架构：目前模型保留 1/8 的标准 softmax attention 部分。我们正在研究更高效、能够完全消除 softmax attention 的架构，有望在没有计算开销的情况下支持无限上下文窗口。
  3. 复杂编程任务：模型的高级编程任务表现有待改善，因为目前预训练阶段编程数据集仍有限。我们持续改进训练数据选择、完善继续训练流程，在下一版本解决这些局限。

D. 部分基准的评测细节

D.1. MMLongBench-Doc

对于上下文长度及图像数量限制无法满足 MMLongBench-Doc 要求的模型，我们采用原仓库7 建议的图像拼接方式：将单个 PDF 输入中提取的所有图像拼接成 5 张，用于所评测的开源模型；对于 Claude-3.5-Sonnet-1022 则拼接成 10 张。评测其他商业模型和 MiniMax-Text-01 时，采用默认配置，最大图像页数设为 120，分辨率设为 144。

D.2. MEGA-Bench

MEGA-Bench 是全面的多模态基准，覆盖 7 种输入格式、6 种输出格式、10 类能力以及包含图像与视频的不同视觉输入。每个请求可能包含多张图像，包括视觉任务描述、请求与回答示范以及视频。对于视频，基准将每段视频切分为多帧，帧数及最终总输入图像数受到模型上下文长度和图像限制约束。确定评测配置时，我们遵循原仓库8 的一般原则，如表 14 所详述。
